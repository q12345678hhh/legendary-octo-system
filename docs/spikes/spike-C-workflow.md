## 1. 方法

在 PostgreSQL 16.15 上建最小工作流模型：实例（带 `version` 乐观锁）、`inbox`（消息键主键去重）、`side_effect`（幂等键唯一）、`compensation`（补偿台账）。处理器按「先入 inbox，再记副作用，同一事务提交」实现。并发用例用两个 psql 进程同时推进同一实例，中间 `pg_sleep(2)` 强制重叠。

## 2. 结果

| 用例 | 场景 | 预期 | 实测 | 结论 |
|---|---|---|---|---|
| 1 | 同一回调投递两次 | applied / duplicate | applied / duplicate | 去重成立 |
| 1b | 副作用计数 | 1 | 1 | 无重复副作用 |
| 2 | 超时后用同键重试 | duplicate，仍 1 | duplicate，1 | 重试安全 |
| 2b | 重试用**不同**键 | 2 | 2 | 键不稳定会重复扣款 |
| 3 | 补偿执行两次 | compensated / replay-skipped | 同预期 | 补偿可重入 |
| 3b | 原副作用 + 补偿净额 | 0 | 0.00 | 可对账 |
| 4 | 顺序陈旧推进 | 0 行，状态不变 | 0 行，version=1 | 乐观锁生效 |
| 5 | **并发**推进（同版本） | 一方 1、一方 0 | A=1，B=0，最终 version=1 | 只有一个胜出 |
| 5b | 最终状态 | 单次迁移 | running-A，version=1 | 无双重推进 |

## 3. 四条固化结论

1. **幂等键必须在业务侧生成且稳定**，不得包含时间戳、重试次数或请求 ID。用例 2b 证明键一变就是重复扣款。
2. **inbox 写入必须先于副作用，且二者同事务**。不变量是「inbox 有条目 ⟺ 副作用已生效」，任一步失败整体回滚，从而可安全重试。
3. **状态推进用条件更新**（`WHERE version = ?`），不用「先查后改」。用例 5 中后到的事务在锁释放后重新求值谓词，得到 0 行，这是正确性来源。
4. **补偿是独立台账**：补偿键独立于原键，记负向副作用，净额可对账（用例 3b 得 0）。

## 4. 明确的边界（不得过度声称）

- 本尖峰只证明**数据库内**副作用恰好一次。若副作用是外部 HTTP 调用，单事务不成立，必须改为 outbox + 至少一次投递 + 接收方幂等，**该链路未验证**。
- 未测：长事务超时、死锁重试、跨实例 saga 的中间态恢复。
- 未定：`inbox` 的归档与分区策略，量级超过千万后需要单独设计。
