# ADR-0005 插件执行器隔离基线

| 项目 | 内容 |
|---|---|
| 状态 | 已接受（尖峰 D 降级验证后） |
| 日期 | 2026-11-09 |
| 依据 | `docs/spikes/spike-D-plugin-isolation.md` |
| 影响 | WP09 集成与插件、WP01-02 测试基线、G3 门禁、G9 门禁 |

## 1. 决策

1. 插件执行器的**正式形态只有一种：容器**。每个执行实例一个容器，一次执行后销毁，不复用。
2. 容器必须同时满足九项基线，缺一不得发布：

   | # | 基线 | 落地方式 |
   |---|---|---|
   | 1 | 非 root 运行 | 镜像内固定 UID，禁止 runtime 以 root 启动 |
   | 2 | 无外网 | 默认 `--network none`；确需出网走网关白名单 |
   | 3 | 只读根文件系统 | `--read-only` + 显式 tmpfs 工作目录 |
   | 4 | 独立 PID/mount/UTS 命名空间 | 由运行时默认提供，不允许 `--pid=host` |
   | 5 | 内存与进程数硬限额 | `--memory`、`--pids-limit`，数值按实测标定 |
   | 6 | CPU 时间上限 | `--cpus` + 执行超时双保险 |
   | 7 | 系统调用白名单 | seccomp profile，禁止 `clone`/`mount`/`ptrace` 等 |
   | 8 | 结束后按容器回收 | 销毁容器即回收 cgroup，禁止残留子进程 |
   | 9 | 数据库与宿主套接字不可达 | 不挂载宿主 `/tmp`/socket 目录；数据库只监听容器网络 |

3. **禁止以「系统用户 + `prlimit` + 网络命名空间」作为生产隔离**。该组合只能用于本地开发与回归演练，且必须标注「非隔离」。
4. 插件能力（文件、网络、密钥）通过**显式挂载与注入**授予，不通过「宿主本来就有的东西」继承。
5. 隔离回归用例（尖峰 D 的 14 项 + 容器特有的 seccomp、只读根两项）纳入 WP01-02 自动化基线，任一用例失败即阻断发布。

## 2. 理由

本次尖峰 D 在降级模式下 14 项用例中 11 项被拦住：读宿主 600 文件、读 `/etc/shadow`、写宿主目录、出网、直连数据库 TCP、200 MiB 内存、CPU 死循环、64 进程 fork 炸弹、宿主环境变量、4 MiB 文件、段错误外溢——全部呈现显式失败形态，可断言。

但有三项失败，且都属于「文件系统视图没被隔离」这同一个根因：

1. 插件以非 root 身份直接读出 `/mnt/c/Windows/win.ini`——WSL 的 drvfs 挂载不遵循 Linux 权限位；
2. 插件连上了 `/tmp/.s.PGSQL.5433` ——`unshare -n` 只清空网络设备，不影响文件系统里的套接字；
3. 在实验集群的 `trust` 配置下，插件以超级用户 `platform_owner` 登录数据库成功。

也就是说，「网络隔离通过了」不等于「数据库不可直连」。`setpriv`/`prlimit` 管的是身份和资源，不改变视图；**视图必须由 mount 命名空间负责**，而这是容器才能稳定提供的。

生产环境的等价风险是：插件能读到同机其他目录、其他租户的临时文件、宿主上的密钥挂载点。这正是 PLAN §12 要求「隔离插件执行器」的原因，不能以本机可行性替代。

## 3. 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 系统用户 + `prlimit` + `unshare -n` 直接上生产 | 无 mount/PID 命名空间与 seccomp，文件系统视图与系统调用面完全暴露（尖峰 D 第 11 项已证伪） |
| 同进程内加载插件（类加载器/子解释器隔离） | 无法限制内存、CPU、系统调用；一次 OOM 或死循环拖垮宿主 |
| 仅靠代码审计与签名，不隔离运行 | 审计无法约束第三方更新与运行时行为，违背「插件不得扩大权限」 |
| 用 systemd 沙箱（`ProtectSystem`/`PrivateNetwork`）替代容器 | 能力接近但依赖宿主 systemd，与「多租户 SaaS 跨环境一致」冲突；可作为容器不可用时的临时兜底，需单独评审 |

## 4. 后果

- 容器运行时**已于 2026-11-09 打通**：WSL2 `pglab` 内 Docker Engine 29.1.3 + Compose 2.40.3（overlayfs、cgroup v2），`dockup` 幂等启动并注入宿主代理，镜像经 `docker.m.daocloud.io` 拉取；`postgres:16` 拉取并运行验证通过（证据 `docs/evidence/docker-engine/verify-output.txt`）。遗留约束：宿主代理对源站 blob CDN 不稳定，大镜像需重试（`dockpull`）；dockerd 随 WSL 会话结束被回收，使用前执行 `dockup`；容器版隔离报告已补（尖峰 D 报告 §7，16 项全部拦住）。
- 每个插件执行都要付出容器启动成本（预估百毫秒级），因此插件调用不能放在同步请求主路径上，必须走异步作业。
- 插件的依赖与运行时由镜像固化，插件升级即镜像升级，需要版本与回滚机制（与 PLAN D-010 一致）。
- 本地开发不具备同等隔离，开发者需知悉「本地通过 ≠ 生产安全」，回归以 CI 容器环境为准。

## 5. 落地检查项

- [ ] WP09 定义插件容器基线镜像与九项运行时参数，写入部署清单。
- [ ] WP01-02 把 16 项隔离用例（14 项 + seccomp + 只读根）接入 CI。
- [x] G3 前完成容器运行时可用性验证，并在证据目录留存容器版隔离报告（2026-11-09：14 项 + 2 项容器专属全部拦住，证据 `docs/evidence/spike-d/container-isolation-output.txt`，分析见尖峰 D 报告 §7）。
- [ ] WP09 插件容器必须以非 PID 1 的子进程执行插件，并由 tini 类监督进程透传退出码；否则 `SIGSEGV` 会被 init 语义吞掉、崩溃被误判为成功（尖峰 D 报告 §7.2-3）。
- [ ] `--memory` 必须与 `--memory-swap` 等值同时设置（或宿主禁用 swap），回归断言以 `memory.peak` 不超上限为准，不以「进程被杀」为准（尖峰 D 报告 §7.2-2）。
- [ ] WP09 明确插件文件交换只走对象存储白名单，禁止宿主目录挂载。
- [ ] 额度数值（内存、pids、CPU）按实测标定后写入配置，不照抄默认值。
