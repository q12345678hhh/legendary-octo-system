# ADR-0003 幂等、状态推进与补偿

| 项目 | 内容 |
|---|---|
| 状态 | 已接受（尖峰 C 验证后） |
| 日期 | 2026-11-09 |
| 依据 | `docs/spikes/spike-C-workflow.md` |
| 影响 | WP09 集成与插件、WP10 AI 执行、WP03 工作流内核、WP01-02 测试基线 |

## 1. 决策

1. 每个入站消息带稳定 `idempotency_key`，由业务事件生成，禁止包含时间戳、重试次数、请求 ID。
2. 处理顺序固定为：写 `inbox`（主键冲突即重复）→ 执行副作用 → 同事务提交。
3. 状态推进使用乐观锁条件更新：`UPDATE ... WHERE id = ? AND version = ?`，检查受影响行数。
4. 补偿走独立台账，记负向副作用，补偿键与原键不同；重放返回跳过，不重复反向。
5. 外部副作用不适用单事务，必须 outbox + 至少一次投递 + 接收方幂等（**待尖峰或 WP09 验证**）。

## 2. 理由

| 决策 | 证据 |
|---|---|
| inbox 先行 | 重复回调返回 duplicate，副作用计数恒为 1（用例 1、1b） |
| 键必须稳定 | 换键重试导致副作用 2 次（用例 2b） |
| 条件更新 | 并发下后到事务得 0 行，最终只迁移一次（用例 5、5b） |
| 补偿独立台账 | 重放 skipped，净额 0.00（用例 3、3b） |

## 3. 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 先查存在再插入 | 并发窗口下两个事务都能查到「不存在」，双写 |
| `SELECT ... FOR UPDATE` 后判断状态再更新 | 可行但代码路径更长，且锁粒度更大；条件更新更简单 |
| 用请求 ID 作幂等键 | 重试会生成新 ID，必然重复（用例 2b 同理） |
| 补偿用同键负数 | 与入站去重冲突，无法区分原操作与补偿 |

## 4. 后果

- 所有写入口必须能构造稳定业务键；没有自然键的场景需要在建模阶段补一个（例如外部系统单号）。
- `inbox` 会持续增长，需要归档策略，量级责任归 WP11-06。
- 外部调用链路的恰好一次尚未成立，任何对外承诺需注明当前实现是至少一次 + 幂等接收。
