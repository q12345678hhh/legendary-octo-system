# ADR-0006 工作助手采集边界

| 项目 | 内容 |
|---|---|
| 状态 | **已废弃（Superseded）**：2026-11-13 需求变更，系统不再监控员工电脑，取消设备侧采集与 Windows 工作助手 |
| 日期 | 2026-11-09（2026-11-13 标注废弃） |
| 依据 | `docs/spikes/spike-F-windows-agent.md`；`IMPLEMENTATION_PLAN.md` Phase 4 需求变更说明 |
| 影响 | 原 WP08 Windows 工作助手、WP06 工时与周报、G4/G6 门禁；现由「语音/文字工时 + AI 周报 + 单据预审」取代 |

## 1. 决策

1. **排除判定先于内容读取**，且是架构不变量而非编码约定：任何采集通道（窗口标题、UIA、DOM、截图、音频、剪贴板）在产生任何内容之前，必须先通过 `CollectionPolicy`；未通过则不得调用内容 API。
2. 排除清单分两层：**硬编码下限**（微信、QQ、TIM、Telegram、DingTalk、Feishu、Slack、Discord 等）不可被租户配置覆盖；**租户强制排除**只能在该下限之上追加，不能删减。
3. 采集到的文本一律经本地最小化与脱敏（邮箱、身份证、银行卡、手机号、长度上限）后才允许进入上报载荷。
4. 上报载荷携带设备身份：设备私钥 ECDSA P-256 签名，`device_id` 由 `MachineGuid` 派生；服务端验签失败即拒收。
5. **语音补充是独立开关**，不得与窗口采集共用一个总开关；不开启时客户端不得持有任何录音句柄。
6. 采集通道升级（例如从标题读取升级到 UIA 正文）必须重新做隐私评审，因为读取面发生了数量级变化。

## 2. 理由

尖峰 F 在真实环境（微信与 QQ 正在运行）证明：策略只读取进程名即可完成排除，`GetWindowTextW` 调用次数为 0，审计日志逐条记录 `content_read=false`。这说明「先判定后读取」在工程上完全可落地，不存在「必须先读一点才能判断」的技术借口。

同时必须承认，本次只验证了**标题级**读取。UIA/DOM 能拿到正文、控件树、甚至输入框内容，读取面比标题大得多；如果不把「先判定后读取」上升为不变量，适配器一多就必然出现绕过路径。

## 3. 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 先读内容再本地过滤掉敏感应用 | 内容已经进入进程内存，进程崩溃转储、恶意插件、调试器都能取到；与「服务端不得接收」无法等价 |
| 只靠服务端丢弃排除应用的数据 | 违反 PLAN D-012「在本地丢弃」；数据已经离开终端，网络与日志侧都可能留存 |
| 用窗口标题关键词识别敏感应用 | 标题可伪造/为空/被本地化；必须按进程身份判定 |
| 把语音采集并入窗口采集总开关 | 用户预期「开工作记录」不等于「允许录音」，会造成隐性录音 |

## 4. 后果

- 新增任何采集适配器都要在策略之后插入，且需要新增一条「排除应用不产生内容」的回归用例。
- 硬编码下限意味着产品需要维护一份应用名单，并随 IM 软件更名（如 WeChat → Weixin）持续更新，需要定期复核机制。
- 设备签名给客户端带来密钥存储问题（DPAPI 保护），服务端需要设备注册、吊销与换机流程。
- 标题级采集的信息量有限，工时质量依赖后续 UIA/DOM 适配；这部分风险在尖峰 F2 单独评估。
