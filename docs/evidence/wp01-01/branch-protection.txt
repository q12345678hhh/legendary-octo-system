二、下发配置（与服务端回读一致）
------------------------------
strict                                  = true
contexts                                = secret-scan, commit-lint, backend, db, frontend,
                                          desktop-agent, plugin-runner, contracts, tests, supply-chain
enforce_admins                          = true
required_approving_review_count         = 0
dismiss_stale_reviews                   = true
allow_force_pushes                      = false
allow_deletions                         = false
required_conversation_resolution        = true
block_creations                         = false
lock_branch                             = false

说明：
1. 必需检查比 docs/runbooks/ci-pipeline.md 原表多一项 db。db 作业在干净的 postgres:16
   服务容器里跑迁移、RLS、并发与校验和门禁，是硬门禁，原表漏列，已同步更新手册。
2. 批准数取 0 是单人阶段的事实约束：GitHub 不允许作者批准自己的 PR，设成 1 会让唯一
   协作者无法合并任何改动。评审要求仍写在手册里，加第二位协作者后必须改为 1 并开启
   code owner 审核——这条不随「当前能合并」而放宽。
3. enforce_admins=true 意味着管理员也不能强推、不能绕过检查，牺牲的是应急直推通道，
   换来的是「门禁对所有人一致」。应急走前向修复，不走强推。

三、负例：直接推送 main 必须被拒绝（实测）
------------------------------------------
本地在 main 上提交后执行 git push origin main：

  remote: error: GH006: Protected branch update failed for refs/heads/main.
  remote:
  remote: - Changes must be made through a pull request.
  remote:
  remote: - 10 of 10 required status checks are expected.
  To github.com:q12345678hhh/legendary-octo-system.git
   ! [remote rejected] main -> main (protected branch hook declined)
  error: failed to push some refs to 'github.com:q12345678hhh/legendary-octo-system.git'

服务端同时给出了两个原因：必须走 PR，且 10 项必需检查尚未在该提交上出现过。
